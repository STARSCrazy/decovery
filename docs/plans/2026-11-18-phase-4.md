# decovery phase 4 — implementation plan: Aztec C86 and the overlay target

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** decovery builds and judges the third target (an MZ program with 13 overlays, small model, Aztec C86 4.2b,
1144 functions, 322 identical in Decomp): an Aztec C86 profile and object reader, overlay loading and overlay
addresses, Aztec prologue search, and build + compare of whole overlay modules including data, relocations and
BSS — done when decovery's verdicts on that target equal Decomp's or differ only in listed deviations where
decovery is right (ADR 0008 step 3).

**Architecture:** `decovery-toolchain` gains the `aztec-c86-*` profiles and `ObjectFormat::Aztec`;
`decovery-objects` gains a clean-room Aztec object and library reader (`aztec.rs`) behind one dispatching
`read_object(format, bytes, name)` that replaces direct `read_omf` calls; a test-only writer builds synthetic
fixtures. `decovery-core` gains the overlay address kind (ADR 0011) and overlay records in the workspace;
`decovery-loaders` reads the overlay table; `decovery-diff` compares an object against the image with link gaps
(there is no Aztec linker step, as in Decomp) and checks whole overlay modules. Migration and bench learn the new
address kind.

**Tech Stack:** Rust stable (edition 2024), crates per ADR 0003 (no new dependency); runners `unicorn-dos` and
`dosbox-lab` (Python plugins).

**Spec:** `docs/design/0001-decovery-design.md` (sections 4, 5.6 `migrate`, 7 phase row 4), ADR 0006 (16-bit
references), ADR 0008 step 3 (`docs/adr/0008-decomp-frozen.md:22-25`). Decomp oracle (read only, frozen; find code
by name, line numbers drift): `src/decomp/nachbau/compiler.py` (`_aztec`), `nachbau/aztec.py`, `nachbau/objekt.py`,
`nachbau/vergleich.py`, `nachbau/module.py`, `formate/overlay.py`, `prologe.py`, `signaturen/` (library layout),
tests `tests/test_aztec.py`, `tests/test_nachbau_overlay.py`.

## Decisions taken in this plan

1. **Order for an early win.** Profile → object reader → runner checkpoint → first verdicts on main-program functions
   (Tasks 1–4) before any overlay work; overlays (5–7), module compare (8), migration (9), parity (10).
2. **Overlay addresses are a new `Address` variant** (ADR 0011, Task 5): canonical text `ovl:<name>:<seg>:<off>`
   (name = overlay name as stored in the workspace, `[A-Za-z0-9_]{1,16}`, upper case; seg/off 4 hex digits), the
   form Decomp writes, so migration maps it 1:1. `linear()` is `None` (an overlay has no fixed linear address).
   One address space per overlay (as Decomp and the ghidra plugin do).
3. **Aztec objects fit the neutral model** unless Task 2 shows otherwise (ADR 0012): unnamed symbols become
   `ObjSymbol { public: false }` with a synthetic name `@<section>:<offset>`; self-relative references become
   `ObjReloc { kind: Relative, target: Symbol(..), frame: Frame::Target }`; no OMF group. ADR 0012 records the
   mapping and, only if needed, the model change.
4. **Clean-room reader.** Written from the documented layout (the compiler's own object header description), not
   by translating Decomp's code; Decomp's tests are the behavioural oracle only. Public fixtures come from a
   test-only writer (`aztec_write.rs`, `#[cfg(test)]`-free but `pub(crate)` under feature `test-writer`).
5. **No Aztec linker.** Verdicts compare the object against the original image, masking link gaps (relocated fields),
   as Decomp does. Linking the whole program is out of scope for phase 4.
6. **Parity baseline is frozen**: Decomp keeps working on this target in unmerged worktrees, so Task 4 step 1
   snapshots Decomp's verdicts into `$DECOVERY_GOLDEN_DIR/aztec/baseline-<date>.json` once; all parity checks use
   that snapshot.
7. **Compiler knowledge** (Decomp's 30 Aztec rules) is migrated as workspace knowledge (Task 9), not into the repo.
8. **Bench stays sparing**: phase 4 needs no bench run; one optional small run (Task 11) only with owner go.

## Global Constraints

- Everything English (ADR 0002). Decomp reports passed through by the bridge stay German.
- Fixed dependencies only (ADR 0003); `unsafe_code = "forbid"` stays.
- No proprietary material: no target or compiler bytes, no objects or libraries produced by the commercial compiler,
  no function names, addresses, hashes or paths of the target. Public tests use objects from the test writer and
  hand-built MZ/overlay bytes. Local tests are `#[ignore = "local: …"]` and read `DECOVERY_LOCAL_WORKSPACE_AZTEC`,
  `DECOVERY_TOOLCHAIN_AZTEC42`, `DECOVERY_DECOMP_WORKSPACE`, `DECOVERY_GOLDEN_DIR`.
- Library code never panics on input; malformed input returns `ObjectError::Malformed { offset, .. }` /
  `Truncated { offset }` naming the byte offset.
- Gates before each commit: `cargo fmt --check`, `cargo clippy -j 2 --all-targets -- -D warnings`,
  `cargo test -j 2`. Stage files explicitly.

## Review Focus

1. **Malformed or truncated Aztec object/library** (wrong magic, item running past THEEND, symbol index out of
   range, library block count past file end) → error with byte offset, never a panic. Owner: Task 2
   (`truncated_object_names_offset`, `symbol_index_out_of_range_is_error`, `library_block_past_end_is_error`).
2. **Decoration collisions**: Aztec appends `_` to functions *and* data; a C name that already ends in `_` or a
   symbol without the suffix (assembler code) must map back unambiguously. Owner: Task 1
   (`trailing_underscore_decoration_round_trips`, `undecorated_symbol_is_kept_verbatim`).
3. **Overlay addresses in every place that takes an address** — CLI/MCP parsing, attempt shard keys, output file
   names, bench task addresses, migration. Expected: `ovl:` parses, prints canonically and gets a key; an unknown
   overlay name is an error naming the known overlays. Owner: Task 5 (`ovl_address_round_trips`,
   `unknown_overlay_name_is_named`), Task 9 (`overlay_attempts_are_migrated`).
4. **Overlay whose header disagrees with the file** (csize past file end, dsize + bss overflow 64 KiB, entry outside
   code) → loader error with offset, other overlays still load. Owner: Task 6
   (`overlay_past_file_end_is_error`, `bad_overlay_does_not_hide_the_others`).
5. **Data and BSS mismatches hidden by a function-only verdict**: a module whose code is identical but data or BSS
   size differs must not be called identical. Owner: Task 8 (`module_with_different_bss_is_not_identical`).
