# Phase 5, step 3: Aztec link and whole-file comparison

Goal: `build` links an Aztec C86 workspace into the root program and its overlays and compares the
whole files with the original, byte for byte. Nothing of the toolchain or the target enters the
repository; tests use synthetic objects and a fake linker.

## Facts (from the third target, verified on the real tool)

- Linker `LN` (v4.10d). Switches: `-o` output, `-f` control file, `-l<name>`, `-b/-c/-d` bases,
  `-s` stack, `+c n` bytes after the code (overlay area), `+d n` bytes after udata, `-r` writes
  `<out>.RSM` (root symbols for overlay links), `-t` writes `.SYM`.
- Root: objects in code order, library objects, then `-l<lib>`. One run.
- Each overlay: its own run: the overlay objects, then `OVBGN.O`, the root's `.RSM`, `-l<lib>`.
- Long input lists go through a `-f` control file (the DOS command line is too short).
- Commons are placed in order of first appearance (an extern counts), reversed within one module;
  a commons-only module therefore goes first. The link order is part of the result.
- Output has no date and no paths: two links give identical files.
- Overlay file header (14 bytes): magic, code origin, code length, data origin, data length,
  udata length, entry.

## Design

1. Profile: `[linker]` for `aztec-c86-4.2b` (`LN {flags} -o {output} {inputs}`), run through the
   same runners as CC and AS. Overlay runs depend on the root run (its `.RSM`).
2. Workspace: `[link]` names the root output, its objects in order, `flags` (e.g. `+c`, `+d`, `-r`),
   and one `[[link.overlay]]` per overlay (output name, objects, flags). Libraries and library objects
   come from `[rebuild]` (ADR 0016). ADR 0018 fixes the keys.
3. Comparison: the whole linked file against the original file.
   - MZ root: header fields named (size, relocations, SS:SP, CS:IP, minalloc, maxalloc), then the image.
   - Overlay: header fields named, then code, then data.
   - First difference named with its region (code, data, header field) and, where the knowledge
     knows it, the function or global at that address.
4. Report: "link: root equal; overlays 13 of 13 equal" (+ JSON per file). A difference fails the build.
5. Order: the root data module (initialised data and udata of the root) is compared before the link
   as main program data, as today; the link comparison then closes the remaining gaps.

## Steps

1. ADR 0018 and the config keys; profile `[linker]`; fake linker in the test runner.
2. Root link run and MZ whole-file comparison with named header fields.
3. Overlay runs against the root's `.RSM`; overlay header comparison.
4. Difference report with region and knowledge name; CLI exit code.
5. Real check on a scratch copy of the third target (one run, `-j 2`).

## Related checks (from the third target)

- A data-only source (no functions) stays `unchecked` in main program data: place it through its
  public symbols that other modules reference.
- An overlay module counted identical before the link while the link order would place its commons
  differently: take the configured link order into the module comparison, or warn.
- Externs without a definition in any linked module show up only at link time: check them in
  `build` against the definitions of the other modules.
